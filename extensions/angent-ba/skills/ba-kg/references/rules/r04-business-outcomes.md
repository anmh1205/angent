# R04: Business outcome before mechanism

## Operational contract

Capture who experiences which problem and how success is measured before declaring device, UI, cloud or framework implementation. Separate the buyer, operator, maintainer and affected customer.

## Checks before accepting an artifact

For each business objective name a measurable outcome, an observation window, a measurement source and the baseline or an explicit unknown. Costs and benefits need a defensible basis, not arbitrary RICE scores.

## Failure response

Consider a process change, use of an existing product, a smaller feature and building a new system. Avoid narrowing the problem to the proposed technology before opportunity validation.

## Grounded example

For a rental fleet, 'reduce time to detect unauthorized vehicle use' is an outcome. 'Use CAN + FreeRTOS' is a technical method whose value still needs testing.

**Evidence boundary:** these checks govern specialist BA deliverables but do not independently authorize provider changes or claim a test ran. ANGENT Root and Execution retain task scope; Quality must inspect the specific output.
